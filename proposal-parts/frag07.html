Section 7: Trust, Compliance, and Accessibility

Accessibility

WCAG 2.2 AA sits inside the build constraints from week one: semantic landmarks and headings, sufficient contrast across components, keyboard navigability without traps, visible focus states, predictable modal behavior, and screen reader labeling that matches what sighted visitors see.

The site publishes an accessibility statement naming the WCAG target, documenting scope limits where third-party embeds apply, and listing a single monitored contact path for fixes and accommodations. We do not ship accessibility overlays. They read as theater for procurement teams while failing substantive audits.

Privacy and data handling

Privacy pages carry a California-aware baseline suited to statewide prospects and CTW's footprint: plain-language notices on collection purposes, retention windows tied to CRM readiness, lawful bases spelled without jargon pile-ons, and routing for deletion or correction requests.

Forms, calculators, and assessments encrypt data in transit with modern TLS configurations and land in stores encrypted at rest with role-scoped access for responders. Cookie consent surfaces appear wherever embedded analytics or optional trackers demand explicit acknowledgment.

Security posture

Cloudflare supplies baseline controls CTW cannot accidentally disable: DDoS mitigation, managed rules via web application firewall patterns tuned for bots and scripted abuse, SSL issuance and renewal on edge endpoints, and rate-aware bot scoring suitable for professional services traffic spikes.

Static publishing strips PHP runtime attack paths and removes plugin-driven CVE churn common on CMS-heavy stacks. Security posture summaries publish beside privacy and accessibility statements so procurement reviewers see deliberate controls rather than quiet promises buried in contracts.

Section 8 translates those foundations into engagement modes sized for CTW's appetite.
